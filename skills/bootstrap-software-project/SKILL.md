# Bootstrap Software Project

Create the **smallest complete, reproducible starting state** for a genuinely new software project. **A request to prepare the architecture/MVP and project documentation in a selected empty or concept-only folder is already a Prepare Bootstrap request**, even if the user does not say "bootstrap", name any skill, or ask to build code. A plain specification or read-only analysis request with no project initialization intent remains an ordinary analysis task. Adapt to the concept and intended platform rather than imposing a framework, language, server, CI provider, or directory tree. The skill **coordinates** existing tools and skills when available, and has a small standalone baseline when optional companion skills are absent; it is not a generic code generator or release system. Never pretend the standalone baseline implements an unavailable companion's protocol or audit.

**Contract authority:** This `SKILL.md` is the sole normative source for new/existing eligibility, companion availability, integrated/mixed/standalone routing and completion gates. `agents/openai.yaml` is only a discovery/entrypoint prompt and must not introduce alternative conditions. `references/first-run-safety.md` contains operational safety checks, not competing routing logic. README and acceptance materials explain and verify this contract; they do not override it.

## Route the request

**Single project-root eligibility rule:** Before choosing Prepare or Build, inventory the **selected** directory and its Git context. An empty or concept-only folder (briefs, requirements, designs, supplied assets) qualifies as a new project; so does a blank clean Git repository at exactly that root. Existing application code, **substantive configuration**, project memory, or a **project-local `AGENTS.md` with maintained project rules** makes it an **existing project**, even if no app code exists. Other maintained project-specific instructions count likewise. Unknown/sensitive files require clarification, not silent initialization or staging. Follow `references/first-run-safety.md` for preservation and Git checks; it must not redefine eligibility differently.

1. **Explore only:** If the user is discussing an idea, comparing options, or expressly avoiding implementation, do not create files, initialize Git, or silently turn the conversation into a project. Help explore using ordinary conversation.
2. **Prepare:** If asked to prepare a **new project**, its architecture/MVP or initial working documentation in an eligible root, own the full project startup workflow (not just architecture prose). Produce a durable project context and product documentation: **when an owner skill is installed and usable, use that owner's canonical output and audit; when absent and not explicitly required, use the documented standalone baseline and native checks**. An installed but failing owner is a blocker, not standalone eligibility. A runnable app is not required. If only a report/review was requested with no project-start intent, do not modify files.
3. **Build:** If asked to create/build a new application or usable initial prototype in an eligible root, do Prepare and then a minimal runnable application skeleton with real launch and verification commands. Do not claim it runs unless actually executed.
4. **Existing project:** If the eligibility check finds meaningful implementation, substantive configuration, project memory, or project-local `AGENTS.md`/maintained project rules, stop *new-project initialization*. Route to existing-project adoption/update workflows; preserve files and Git history. Never re-bootstrap over existing user work.

The user's explicit task and approved scope outrank these defaults. Ask **only** for missing choices that materially change the architecture, storage/security boundary, target platform, distribution model, or first useful outcome. If several decisions are needed, present a compact proposed baseline and ask approval of those decisions together. Don't demand a formal specification from an informal concept.

## Establish input, authority, and target

- Determine the intended project root from an explicit user-selected folder/workspace. Do not guess a writable destination. Resolve the real path and inspect contents and enclosing version-control roots before writes. Classify new versus existing by the **single eligibility rule in Route the request**; preserve supplied source documents and existing history.
- Gather a **bounded** input pack from files in that folder and the current Codex conversation: concept, MVP, sketches, constraints, expected usage, target platforms, relevant decisions. Include user-provided Markdown and ordinary prose equally. Never claim to see another ChatGPT/Codex conversation unless its content was supplied or an authorized connector actually retrieved it.
- Order authority: current user direction and project rules; explicitly approved concept/MVP decisions; other supplied requirements; current implementation evidence; provisional ideas. Record uncertain claims as Proposed, Unverified, or Open — not silently Approved.
- Determine product shape, supported platforms, users, interaction model, network/offline needs, data persistence, sensitivity, packaging/distribution, operational footprint, and MVP boundary. The categories are **axes**, not fixed stack presets: see `references/project-assessment.md`.
- Prefer established native platform tooling and reusable/open-source components to invented infrastructure. Verify current compatibility when online sources are available. If unavailable, make dependencies/assumptions explicit and avoid fabricated version claims.

## Make a small bootstrap contract

Before substantial writes, state: (a) project root and whether it is empty/concept-only; (b) Prepare or Build; (c) inferred project type and target platforms; (d) proposed MVP, exclusions, main technical choices and unresolved blockers; (e) Git initialization/commit authorization; (f) checks that will establish success. Ask for approval only where the user's previous instructions do not establish the necessary consent. This is not permission to publish or deploy.

Read `references/first-run-safety.md` for filesystem/Git safety and the minimal completion contract. Do not change global `~/.codex/AGENTS.md`, an existing project's `AGENTS.md`, user credentials, cloud resources, or package registries without separately applicable authority.

## Early Git author/committer identity preflight

After determining the selected root and before substantial project writes or staging, check whether Git can make the planned first commit. GitHub, GitLab and remotes are **not required** and must not be queried to invent identity. Read effective repository/global/system/conditional Git configuration and relevant `GIT_AUTHOR_*` / `GIT_COMMITTER_*` environment overrides. Prefer `git config --show-origin --show-scope` diagnostics plus `git -c user.useConfigOnly=true var GIT_AUTHOR_IDENT` and `GIT_COMMITTER_IDENT` checks, accounting for identity injected by authorized environment variables; do not accept hostname/OS auto-guesses as confirmed user choices. Treat local `user.name` and `user.email` as ordinary commit metadata, never authentication.

If valid explicit author **and** committer identity cannot be established, ask **one direct intermediate question** for commit name/email and whether to save them only in this repo or globally. An email need not correspond to a GitHub account or live inbox; `noreply` is optional only if the user supplies/approves the exact service-specific address. Never embed user identity in this public skill, infer it from a remote/account handle, invent a `noreply` address, or set global Git config without explicit permission. A repo-local value can be written only after authorized `git init`; re-check effective identity before commit. If approval/identity is missing, safely pause, preserve all files/index and report **ENVIRONMENT / INCOMPLETE** rather than trying a fake author. See `references/first-run-safety.md`.

## Execute by ownership and in order

1. **Inspect and classify.** Read only relevant inputs, inventory the target folder and possible parent Git root, resolve critical choices. Apply the **single eligibility rule** before writes. Classify pre-existing content as (a) concept/requirements/design inputs, (b) actual application code, substantive configuration or maintained project-local rules (existing-project route), (c) assets and large/binary/licensed files, or (d) unrelated/unknown/sensitive files (stop and ask). Preserve input bytes; for files at risk of being changed, record pre-write checksums. Link to existing briefs rather than rewriting them. Inventory separately what may be **tracked** in the initial commit; no automatic binary/license-sensitive staging merely because files were present. No indiscriminate staging, deletion, moving or cleanup.
2. **Establish local Git.** A new full-fledged project should use Git by default. **`Local Git commit policy: auto` does not itself authorize `git init`.** Initialize Git only when the user has explicitly approved this new-project bootstrap including its default local Git behavior, or approved Git initialization for this target. Such approval may be a standing instruction for the user's nominated new-project folders. If absent, present it as a standard part of the bootstrap contract and obtain consent before executing. When a clean Git repository already exists at the exact intended root, reuse it without re-running `git init`; inspect HEAD/index/branch first. Never initialize an enclosing workspace or nested repository by accident. Use native Git; never create a GitHub remote implicitly.
3. **Establish durable project context.** Determine dependency availability before writing. If `maintain-project-memory` is **installed and usable**, invoke its **Bootstrap** owner and require its canonical `AGENTS.md`, `docs/project-memory/` and owner audit for both Prepare and Build. Use its current approved template and update policy. New projects using that workflow may adopt `Local Git commit policy: auto`. If that owner is **not installed**, use **standalone mode**: create a concise project-local `AGENTS.md` (scope/rules) and minimal `docs/project-notes/` with status, decisions and next action; do not copy the absent owner's schema, claim `maintain-project-memory/v2` compatibility or report its audit as passed. If the owner is installed but fails, is incompatible or is not write-eligible, stop that owner-dependent gate as **BLOCKER / INCOMPLETE**; do not silently downgrade to standalone. If the user explicitly requires a particular unavailable protocol, ask for installation/approval rather than substitute a lookalike. Do not invent approval provenance or alter decision history.
4. **Create product documentation.** If `project-documentation` is installed and usable, invoke its **init** and audit to document real requirements and accepted design in `docs/project-knowledge/`. If absent, create only a small native Markdown baseline (e.g. `README.md`, `docs/ARCHITECTURE.md`, `docs/MVP.md`) with verified relative links and honest Proposed/Open distinctions; do **not** claim the absent owner's audit passed. If the owner is installed but fails or is not write-eligible, mark **BLOCKER / INCOMPLETE**, not an invisible fallback. Create an accurate root `README.md`; do not generate API, schema, or release documentation for nonexistent implementation.
5. **Create technical foundation (Build only).** Choose the simplest mature platform-native generator or existing template appropriate to the accepted project shape, then scaffold the least useful runnable slice. Create an appropriate `.gitignore` before staging anything. Use deterministic dependency files/lockfiles where supported. Add clear local setup/run/test commands; use actual smoke tests. CI configuration is appropriate only when real executable checks and a chosen provider exist; do not invent passing CI or assume GitHub publication.
6. **Verify and checkpoint (mode-aware completion gate).** After Build, update documentation to reflect what actually runs, never merely proposed behavior. **Before staging or claiming a successful Bootstrap**, validate the applicable ownership gates:
   - **Integrated memory gate (owner installed):** project-local `AGENTS.md` declares `Project memory protocol: maintain-project-memory/v2`, `Project memory schema: project-memory/v1`, `Canonical project-memory root: docs/project-memory`, a valid `Memory update policy`, and the agreed `Local Git commit policy`. All five canonical `docs/project-memory/PROJECT.md`, `STATUS.md`, `DECISIONS.md`, `SESSION_LOG.md`, `HANDOFF.md` exist. Actually run the owner's `audit_project_memory.py <project-root>` with success. An installed but failed owner is **BLOCKER / INCOMPLETE**. A generic documentation audit or clean Git status cannot replace it.
   - **Standalone memory gate (owner absent):** verify a truthful `AGENTS.md`, minimal `docs/project-notes/` status/decisions/next-action and links, without fabricated canonical protocol markers or invented audit evidence. This *can* be PREPARED (standalone) when the user did not require the absent protocol.
   - **Integrated documentation gate (owner installed):** actually run the owner's current documentation audit, including Markdown links and Git-whitespace checks; failure is **BLOCKER / INCOMPLETE**.
   - **Standalone documentation gate (owner absent):** review README, scope/MVP and architecture docs, labels for unapproved choices, relative links and native `git diff --check` where Git is available. Never label these as the unavailable owner audit.
   - **Both modes:** check setup/entrypoint/tests if Build, scope and security/data boundaries, preserved input files, selective staged paths, early and final Git identity, and correct provenance of decisions. Have an available memory owner record a factual checkpoint; otherwise record the outcome in standalone notes.
   - **If an owner was explicitly required but is absent**, declare **INCOMPLETE** pending installation rather than downgrading. Do not claim PREPARED or BUILD READY when an applicable gate has failed.

7. **Make a scoped local commit only after the mandatory memory and documentation gates pass.** Follow `maintain-project-memory`'s `references/local-git-checkpoints.md` when available. Stage only reviewed task-owned paths, verify cached diff and `git diff --cached --check`, then commit once if authorized and safe. Existing staged work, changing HEAD, ambiguous ownership, secrets, or failed checks **stop** the commit. Never bypass hooks or clean/reset unrelated files. No push, remote repo, tag, release, installer publication or deployment.

## Completion states

- **PREPARED:** approved scope, durable context, honest product documentation, passing **applicable** gates, and a truthful next action exist. Evaluate memory and product-documentation owners **independently**: for each installed owner require its canonical files and actual audit; for each genuinely absent, non-required owner require the verified standalone baseline and native checks. An installed-but-failing or explicitly required-but-absent owner makes this **INCOMPLETE**, even if Git is clean.
- **Report mode:** identify **integrated** (both owners installed), **standalone** (both absent), or **mixed** (only one installed). These describe evidence, not different permissions or new schemas. Never report an unavailable owner's audit as passed.
- **BUILD READY:** applicable Prepare gates passed and the intended minimal application actually starts or runs, with documented dependencies and development commands.
- **INCOMPLETE / ENVIRONMENT:** missing author/committer identity, required approvals, Git/tools, broken owner checks, unclear ownership, or blocked runtime prevent a claimed outcome. Preserve partial artifacts and report the exact next safe action. A clean documentation audit alone does not prove a runnable application.

For the standard full-project bootstrap, consider the local Git repository and first safe local commit part of readiness unless the user expressly opted out. No remote service activity is ever implied.

## Final report

Include: inferred project type/platform, Prepare/Build result (**integrated**, **mixed** or **standalone**), initial folder classification and preserved files, MVP scope and key decisions/assumptions, created files, **the specific skills actually invoked (distinguish discovered/read from applied or absent)**, and real checks/outcomes. Report the applicable memory paths/policies and memory audit result **or its honest absence**, applicable documentation audit **or native checks**, Git identity readiness without exposing private values unnecessarily, Git root/branch/full local SHA and committed path count, remaining dirty files, external dependencies and next action. If any mandatory result is unknown, label it **NOT VERIFIED**, not PASS. Distinguish proposed, written, tested, committed, published, installed and running states. Do not write a success claim before actually validating it.
